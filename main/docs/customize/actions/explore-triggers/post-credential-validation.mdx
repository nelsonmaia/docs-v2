The `post-credential-validation` trigger runs during a login to a database connection, immediately after the connection validates the submitted credential and before Auth0 returns a response to the browser or calling application. It also runs before multi-factor authentication (MFA) is evaluated. Unlike [`post-login`](/docs/customize/actions/explore-triggers/post-login), this trigger runs on **both** successful and failed credential checks, and it runs before Auth0 has composed any response — so a denial from an Action on this trigger is returned by Auth0 in the same shape as a wrong-credential response, rather than as a distinguishable error.

Actions in this flow are blocking (synchronous): they execute as part of the trigger's process and prevent the rest of the Auth0 pipeline from running until the Action completes.

## How it works

Auth0's Universal Login validates a submitted credential and answers the request with a redirect. The [`post-login`](/docs/customize/actions/explore-triggers/post-login) trigger runs **after** that redirect has already been decided, so an Action on `post-login` cannot change the credential outcome — it can only deny the login afterwards, with a different, distinguishable error.

The `post-credential-validation` trigger runs **before** Auth0 composes any response:

<Frame>![Diagram showing where post-credential-validation runs in the login flow: after the database connection validates the credential and before Auth0 returns a response to the browser. The trigger runs on both success and failure outcomes. post-login only runs after a successful authentication, downstream of this trigger.](/docs/images/customize/actions/post-credential-validation-trigger-flow.svg)</Frame>

When a user submits a credential, the database connection validates it first. The `post-credential-validation` trigger fires immediately after that validation, on both successful and failed attempts, before Auth0 has returned any response and before MFA is evaluated. An Action can allow the flow to continue (the default), or deny it — and because the trigger runs before Auth0 has composed its response, the end user sees the same response whether the Action denied a valid credential or the credential itself was wrong. The `post-login` trigger only fires further downstream, and only if authentication ultimately succeeded.

| | `post-login` | `post-credential-validation` |
| --- | --- | --- |
| Runs | After Auth0 decides the response | Before Auth0 decides the response |
| Runs before MFA | No — MFA has already run | Yes |
| Runs on failed credential checks | No | Yes |
| Can change the credential outcome | No | Yes — can deny a valid credential |
| Denial response seen by the end user | Distinguishable from an invalid credential | Identical to an invalid credential |
| Available on all database connection modes and authentication methods | Yes | Yes |

### Why the denial response matters

Auth0 composes its response to the login request only after every Action on this trigger has run. Because of that, when an Action denies a login here, Auth0 returns the same response — the same status, body, and redirect behavior — that it returns for a wrong credential. From the shape of that response alone, the end user can't tell the two outcomes apart.

This only covers the response Auth0 returns. It doesn't cover side channels your Action's own code can introduce, such as response time. If your Action does more work on one branch than the other — for example, calling an external service only when the credential is valid — that difference in latency can itself be a signal. If that matters for your use case, consider adding an artificial delay to the faster branch so both branches take a similar amount of time.

## Credential outcomes

The Action runs on both outcomes of the credential check. Branch on `event.credential.valid`:

| `event.credential.valid` | Meaning | What the Action can do |
| --- | --- | --- |
| `true` | The submitted credential passed validation | Allow (default) or deny |
| `false` | The submitted credential failed validation | Report or record the attempt. The authentication still fails. |

An Action cannot promote a failed credential check to a success. On the failure path, use the Action to send signals to an external system, such as reporting the attempt to a fraud or risk pipeline.

<Note>

On the failure path the account may not exist, so `event.user` is not always available. Use optional access, such as `event.user?.email`.

</Note>

## Common use cases

### Deny a high-risk login before Auth0 responds

A `post-credential-validation` Action can call an external risk or fraud decision service and deny the login before any response has been returned to the end user:

```javascript lines
/**
 * @param {Event} event - Details about the credential
 *   validation and the context of the login.
 * @param {PostCredentialValidationAPI} api - Methods to
 *   influence the outcome of the login.
 */
exports.onExecutePostCredentialValidation = async (
  event,
  api
) => {
  if (!event.credential.valid) {
    return;
  }

  const { code } = await callRiskDecision(
    {
      ip: event.request.ip,
      userId: event.user.user_id,
    },
    event.secrets
  );

  if (code === "deny") {
    api.authentication.deny({
      reason: `Risk service denied the login: ${code}`,
    });
  }
};
```

<Note>

An Action on this trigger runs on the synchronous credential-verification path, so its execution time is added to every login attempt. Apply a bounded timeout to any external call the Action makes.

</Note>

### Report failed credential checks to a fraud pipeline

Because this trigger also runs when the submitted credential is invalid, it can be used to report failed attempts without changing the login outcome. `event.user` is not always available on the failure path, but `event.credential.identifier` echoes back the identifier the user submitted, so the attempt can still be reported against it:

```javascript lines
/**
 * @param {Event} event - Details about the credential
 *   validation and the context of the login.
 * @param {PostCredentialValidationAPI} api - Methods to
 *   influence the outcome of the login.
 */
exports.onExecutePostCredentialValidation = async (
  event,
  api
) => {
  if (event.credential.valid) {
    return;
  }

  try {
    await reportFailedAttempt({
      ip: event.request.ip,
      method: event.authentication?.methods?.[0]?.name,
      identifier: event.credential.identifier,
    });
  } catch (err) {
    // Reporting must not affect the login outcome.
  }
};
```

### Share data with Post-Login Actions

A `post-credential-validation` Action can pass arbitrary data forward to [`post-login`](/docs/customize/actions/explore-triggers/post-login) Actions in the same transaction using [Actions Transaction Metadata](/docs/customize/actions/transaction-metadata). This is useful when a decision made during credential validation — such as a risk score — should also be available to Actions that run after the login completes.

```javascript lines
exports.onExecutePostCredentialValidation = async (
  event,
  api
) => {
  if (!event.credential.valid) {
    return;
  }

  const { score } = await callRiskDecision(
    event.user.user_id,
    event.secrets
  );
  api.transaction.setMetadata("riskScore", score);
};
```

An Action on `post-login` then reads the shared value:

```javascript lines
exports.onExecutePostLogin = async (event, api) => {
  const score = Number(event.transaction?.metadata?.riskScore ?? 0);

  if (score > 0.5) {
    api.multifactor.enable("any");
  }
};
```

<Note>

Transaction metadata set on `post-credential-validation` is available on `post-login` for every successful authentication method on a database connection — password, passkey, email one-time code, and phone one-time code — regardless of whether the connection uses Custom Database scripts or import mode.

</Note>

## Configure the trigger

The trigger is part of the Login flow. To add an Action:

1. Navigate to [Auth0 Dashboard > Actions > Triggers](https://manage.auth0.com/#/actions/triggers).
2. Select the **post-credential-validation** trigger.
3. Add one or more Actions. Actions run in sequence.

The Action handler is `onExecutePostCredentialValidation`:

```javascript lines
/**
 * @param {Event} event - Details about the credential
 *   validation and the context of the login.
 * @param {PostCredentialValidationAPI} api - Methods to
 *   influence the outcome of the login.
 */
exports.onExecutePostCredentialValidation = async (
  event,
  api
) => {
  // Code goes here
};
```

The trigger is bound to the Login flow, not to an individual connection. To scope an Action to one connection, branch on `event.connection.name` or `event.connection.id`.

## Supported connections and authentication methods

The trigger runs for database connections in every configuration:

| Connection mode | Supported |
| --- | --- |
| Custom Database scripts enabled | Yes — runs after the `login` script completes, whether or not import mode is turned on |
| Custom Database scripts disabled | Yes — runs after Auth0's credential check against the user store completes |

The trigger runs for all authentication methods on database connections: password, passkey, email one-time code, and phone one-time code.

## Limitations

| Limitation | Detail |
| --- | --- |
| Signup | The trigger does not run when a user registers. Use `pre-user-registration` or `post-user-registration`. |
| Non-database connections | The trigger runs for database connections only. Social and enterprise connections have no credential-validation step in Auth0. |
| Passwordless connections | [Passwordless Authentication Methods](/docs/authenticate/passwordless/authentication-methods) using a passwordless connection are not supported. |
| Profile and token changes | The trigger cannot modify the user profile, metadata, tokens, or claims. Use `post-login` for those changes. |
| Failed credential checks | The trigger cannot turn a failed credential check into a success. |
| Multi-factor authentication | `post-credential-validation` runs before MFA. The trigger doesn't expose `api.multifactor`. |
| `event.credential.identifier` on passkey logins | Passkey logins never submit a typed username or email, so `event.credential.identifier` is the WebAuthn credential ID instead — not a value the user typed. |

### Latency and error handling

This trigger **fails closed**. If the Action throws, times out, or the Actions runtime is unavailable, Auth0 rejects the login rather than allowing it to proceed on its original credential outcome. Both failure cases return a response that is identical whether or not the submitted credential was valid, so an outage doesn't let an attacker use the response to determine whether an account exists.

<Note>

An Action does not need its own `try`/`catch` to reject logins when an external service is unavailable — the platform already fails the login closed. Catching the error and calling `api.authentication.deny()` explicitly is still useful: it lets you record your own reason in the tenant log instead of a generic error.

</Note>
